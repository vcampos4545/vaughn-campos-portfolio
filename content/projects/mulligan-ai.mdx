## Overview

A healthcare platform that processes insurance denial documents and helps
generate appeals with AI. Insurance denials are common, slow to appeal, and
disproportionately burden patients and providers who don't have the time or
expertise to write a strong appeal letter. Upload a denial document, and
Mulligan AI extracts the relevant details and drafts a supporting appeal.

## Problem

Writing an appeal means synthesizing a denial letter, the underlying medical
claim, and applicable policy language into one coherent, persuasive document.
That process is manual, slow, and inconsistent across providers. The platform
needed to:

- Reliably extract structured data (denial reason, claim details, policy
  references) from unstructured, inconsistently formatted documents
- Generate appeal drafts that stay grounded in the source documents instead of
  reading as generic or hallucinated
- Handle sensitive healthcare data with an architecture appropriate for that
  responsibility
- Support a real multi-user workflow (accounts, document history, review)
  rather than a single-shot script

## Technical Architecture

/>

- **Frontend (Next.js/React).** The upload, review, and appeal-editing
  interface, built for fast iteration and a straightforward Vercel deployment.
- **Data layer (Supabase/Postgres).** User accounts, document metadata, and
  generated appeal records, using row-level security to scope data access per
  user.
- **AI pipeline (LLMs).** Document text extraction feeds an LLM pipeline that
  identifies denial reason codes and claim details, then drafts an appeal
  grounded in that extracted context.
- **Infrastructure (AWS).** File storage and background processing run
  alongside the Supabase-hosted data layer.

## Implementation Details

<Figure
  label="Data pipeline"
  kind="diagram"
  caption="From raw document upload to structured extraction to generated appeal."
/>

The pipeline is staged rather than a single end-to-end prompt. Documents are
parsed into structured fields (denial reason, dates, policy references)
first, and only then does the generation step draft the appeal, grounded in
those fields rather than the raw document text. That keeps the generation
step's context tight and makes failures easier to trace to either extraction
or drafting.

Postgres row-level security policies scope every query to the authenticated
user, so access control is enforced at the database layer rather than relying
on application checks alone.

## Challenges

The central challenge is reliability. An appeal letter with a fabricated
detail is worse than no appeal at all in a healthcare context. Grounding
generation in explicitly extracted fields, rather than free-form summarization
of the source document, was the main mitigation. Surfacing those fields to
the user for review before an appeal is finalized keeps a human in the loop
instead of running the system fully autonomously.

Working with healthcare-adjacent documents also raised the bar on data
handling across the stack: storage, access control, and logging all needed
more care than a typical CRUD app.

## Results

The platform takes a user from an uploaded denial document to a reviewed,
ready-to-submit appeal draft in one guided workflow, replacing what would
otherwise be manual document review and writing.

## Lessons Learned

Splitting the LLM pipeline into extraction and generation stages, with a
human review checkpoint in between, produced much more trustworthy output
than a single end-to-end generation step, and made failures far easier to
diagnose.

## Future Work

- Add appeal-outcome tracking to build a feedback loop on which strategies succeed
- Expand structured extraction to cover more denial and policy formats
- Add provider-side collaboration features for multi-person appeal review
