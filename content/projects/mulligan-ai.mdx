## Overview

A healthcare platform that processes insurance denial documents and helps
generate appeals with AI. Insurance denials are common, slow to appeal, and
disproportionately burden patients and providers who don't have the time or
expertise to write a strong appeal letter. Upload a denial document, and
Mulligan AI extracts the relevant details and drafts a supporting appeal.

## Problem

Writing an appeal means synthesizing a denial letter, the underlying medical
claim, and applicable policy language into one coherent, persuasive document.
That process is manual, slow, and inconsistent across providers. The platform
needed to:

- Reliably extract structured data (denial reason, claim details, policy
  references) from unstructured, inconsistently formatted documents
- Generate appeal drafts that stay grounded in the source documents instead of
  reading as generic or hallucinated
- Handle sensitive healthcare data with an architecture appropriate for that
  responsibility
- Support a real multi-user workflow (accounts, document history, review)
  rather than a single-shot script

## Technical Architecture

- **Frontend (Next.js/React).** The upload, review, and appeal-editing
  interface, built for fast iteration and a straightforward Vercel deployment.
- **Data layer (Supabase/Postgres).** User accounts, document metadata, and
  generated appeal records, using row-level security to scope data access per
  user.
- **RAG pipeline (OpenAI embeddings + Pinecone).** Uploaded documents are
  chunked, embedded, and stored in a Pinecone vector index scoped per appeal.
  Generating an appeal runs a retrieval step first: a query built from the
  denial reason gets embedded and searched against that appeal's chunks, and
  the closest matches are pulled into the prompt as grounding context.
- **Infrastructure (AWS).** File storage and background processing run
  alongside the Supabase-hosted data layer.

## Implementation Details

Documents are extracted to raw text (PDF, Word, or plain text), then split
into roughly 1,000-character chunks and embedded with OpenAI's
`text-embedding-ada-002`. Each chunk is upserted into Pinecone with metadata,
appeal ID, document type, file name, chunk index, so a query can be scoped to
one appeal's documents instead of searching across every user's data at
once. The embedding model outputs 1536 dimensions, but the Pinecone index is
provisioned at 1024, so every vector gets truncated before storage and every
query embedding gets truncated the same way before search, keeping the two
sides consistent.

Very short documents, denial letters under about 1,000 characters, skip the
vector store entirely and get passed straight into the prompt. Chunking and
embedding a single paragraph adds a network round trip without adding
anything retrieval would find, so the small-document path is a plain
pass-through instead of forcing everything through the same pipeline.

At generation time, the denial reason forms a search query, gets embedded,
and is matched against Pinecone with a metadata filter on `appealId`. The
top results come back as raw text chunks, get stitched into the prompt
alongside the structured fields already extracted from the denial letter,
and only then does the model draft the appeal. Retrieval happens before
generation on every request, so the draft is grounded in whatever was
actually uploaded for that appeal rather than the model's general knowledge
of insurance policy language.
