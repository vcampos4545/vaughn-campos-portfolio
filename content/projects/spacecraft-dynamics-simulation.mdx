## Overview

A general-purpose rigid-body physics library in C++, built around a small set
of composable joint primitives and a from-scratch collision/constraint
solver, with spacecraft scenarios layered on top as examples rather than
baked into the engine. The physics core (`rigidbody`) doesn't know what a
"spacecraft" is or how flight software should behave. It only knows about
rigid bodies, actuators, and constraints. Everything spacecraft-specific,
like a 1U cubesat's attitude-control stack or a multi-body Falcon 9 with
stageable joints, lives in example scenarios that consume the library the way
real flight software consumes a physics engine: define the vehicle, then read
sensors and command actuators every tick.

## Problem

The project started as one monolithic spacecraft simulator: orbital
mechanics, attitude propagation, and a fixed flight-software stack all
compiled into a single engine. That worked for the original goal of
experimenting with attitude controllers, but it didn't generalize. Physics
and spacecraft-specific code were tangled together, so reusing the engine for
anything else meant fighting assumptions baked in from day one. The joint
system was similarly minimal: one ad hoc fixed joint and a rope constraint,
with no shared structure between them.

Turning it into something reusable meant:

- Separating the physics engine from spacecraft-specific gravity models and
  flight software, so it could simulate any rigid body, not just a satellite
- Replacing the one-off joints with a small, standard set of constraint
  primitives that share their underlying math instead of duplicating it
- A way to validate constraint behavior precisely, rather than eyeballing it
  in the viewer

## Technical Architecture

  label="Library / example split"

The project is now split into a physics library and a set of examples that
consume it:

- **`rigidbody` (the library).** `RigidBody` (box/sphere/cylinder/cone,
  mass/inertia from density or mass, GJK+EPA convex collision), `PhysicsWorld`
  (fixed-timestep Sequential-Impulse solver, 120 Hz), and a constraint system:
  `FixedConstraint`, `PointConstraint`, `HingeConstraint`, and
  `SliderConstraint`, each removing a specific set of the 6 relative degrees
  of freedom between two bodies, built from shared solver blocks so a new
  joint is an assembly of existing pieces, not a rewrite. A
  `DistanceConstraint` (rope/string) covers the one case the other four can't
  express. Actuators (`ReactionWheel`, gimbaled `Thruster`) are physical
  primitives attached to a body, independent of any specific vehicle. The
  library has zero rendering dependency and builds standalone via CMake.
- **Examples.** Six self-contained scenarios, rendered with a small custom
  OpenGL layer ([VGL](https://github.com/vcampos4545/VGL)), that each define a
  vehicle from the library's primitives and write their own flight software: a
  cubesat with a full PID/LQR/cascaded attitude-control stack, a multi-body
  Falcon 9 with in-flight staging, a Calder mobile, two independently
  deployable solar panels, a rigid chain, and a telescoping antenna boom.

## Implementation Details

Collision between arbitrary convex shapes runs through GJK for intersection
and EPA for contact resolution, feeding a Sequential-Impulse solver with
Baumgarte position-error correction shared across every constraint type.
Attitude is represented with quaternions throughout, renormalized after each
integration step to prevent drift, with Euler's rigid-body equation driving
angular dynamics under applied and disturbance torques.

The cubesat example's flight software is a small, literal pipeline: guidance
computes a target attitude, control (PID, LQR, or cascaded rate/attitude,
selectable at runtime) acts on it, and actuator allocation converts that into
individual reaction-wheel commands via the wheel configuration's
pseudo-inverse. All of it lives in the example, not the engine, so swapping
controllers never touches physics code.

## Challenges

The most instructive bug wasn't in the new constraint math. It was a latent
issue the constraint refactor exposed. A welded rocket nose cone stopped
rigidly tracking the rocket body under thrust, visibly spinning away from it
over a few seconds. The instinctive suspect was Baumgarte overcorrection, so
I clamped the correction term, and the bug didn't change at all, bit-for-bit
identical across a 5-second reproduction.

That ruled out my first theory immediately, which was the point of building
a headless reproduction: a small standalone program with the exact rocket and
nose-cone masses, no GUI, printing orientation state every physics step. A
`beta = 0` run (no position correction at all) produced the same divergence,
meaning the bug wasn't in the Baumgarte term. Instrumenting the solver
directly showed the real cause: a Cramer's-rule linear solve used an absolute
numerical singularity threshold (`|determinant| < 1e-10`). A 549-tonne
rocket's inverse inertia is naturally tiny in SI units, so the rotational
constraint's determinant fell under that threshold even though the matrix
was perfectly well-conditioned. The rotational correction was silently
returning zero, every step, for that one mass scale, while the translational
half kept working and quietly injected unopposed angular velocity into the
cone every frame. Nothing crashed. It just did nothing, and only at
spacecraft scale.

## Results

Making the singularity check scale-relative instead of absolute fixed it. The
same reproduction now holds the nose cone's orientation to the rocket's
within about 0.001 degrees, under the same torque that previously diverged
past 180 degrees in under 5 seconds. Each constraint primitive has its own
targeted headless test (a pendulum arm holding length, a piston sliding with
zero lateral drift, a hinge settling exactly at its limit) that ran clean
before and after the fix, confirming the change was surgical rather than
incidentally fixing one thing while breaking another.

## Lessons Learned

Debugging physics by watching a render is slow and ambiguous. "It looks
wrong" isn't falsifiable. A headless harness that just prints numbers turned
a vague visual symptom into a precise measurement, and let me disprove a
plausible first hypothesis in minutes instead of an afternoon. Numerical
thresholds tuned at one scale can fail silently at another without ever
erroring, which is a much easier bug to miss than one that's loud. Building
the constraint system out of small, shared, independently testable solver
blocks paid off immediately: the fix applied uniformly across every joint
type built from that code, not just the one that surfaced the bug.
