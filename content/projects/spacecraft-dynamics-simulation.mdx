## Overview

A general-purpose rigid-body physics library in C++, built around a small set
of composable joint primitives and a from-scratch collision/constraint
solver, with spacecraft scenarios in mind.

## Problem

This started out as one monolithic spacecraft simulator: orbital mechanics,
attitude propagation, and a fixed flight-software stack all built into a
single engine. That was fine for what I originally wanted, messing around
with attitude controllers, but it didn't generalize at all. Physics code and
spacecraft-specific code were tangled together, so anytime I wanted to reuse
the engine for something else I ended up fighting assumptions I'd baked in
on day one. The joint system had the same problem, just one ad hoc fixed
joint and a rope constraint, no shared structure between them.

Making it actually reusable meant:

- Separating the physics engine from spacecraft-specific gravity models and
  flight software, so it could simulate any rigid body, not just a satellite
- Replacing the one-off joints with a small, standard set of constraint
  primitives that share their underlying math instead of duplicating it
- A way to validate constraint behavior precisely, rather than eyeballing it
  in the viewer

## Technical Architecture

It's now split into a physics library and a set of examples that use it:

- **`rigidbody` (the library).** `RigidBody` (box/sphere/cylinder/cone,
  mass/inertia from density or mass, GJK+EPA convex collision), `PhysicsWorld`
  (fixed-timestep Sequential-Impulse solver, 120 Hz), and a constraint system:
  `FixedConstraint`, `PointConstraint`, `HingeConstraint`, and
  `SliderConstraint`, each removing a specific set of the 6 relative degrees
  of freedom between two bodies, built from shared solver blocks so a new
  joint is an assembly of existing pieces, not a rewrite. A
  `DistanceConstraint` (rope/string) covers the one case the other four can't
  express. Actuators (`ReactionWheel`, gimbaled `Thruster`) are physical
  primitives attached to a body, independent of any specific vehicle. The
  library has zero rendering dependency and builds standalone via CMake.
- **Examples.** Six self-contained scenarios, rendered with a small custom
  OpenGL layer ([VGL](https://github.com/vcampos4545/VGL)), that each define a
  vehicle from the library's primitives and write their own flight software: a
  cubesat with a full PID/LQR/cascaded attitude-control stack, a multi-body
  Falcon 9 with in-flight staging, a Calder mobile, two independently
  deployable solar panels, a rigid chain, and a telescoping antenna boom.

## Implementation Details

Collision between arbitrary convex shapes runs through GJK for intersection
and EPA for contact resolution, feeding a Sequential-Impulse solver with
Baumgarte position-error correction shared across every constraint type.
Attitude is represented with quaternions throughout, renormalized after each
integration step to keep drift from creeping in, with Euler's rigid-body
equation driving angular dynamics under applied and disturbance torques.

The cubesat example's flight software is a pretty literal pipeline: guidance
computes a target attitude, control (PID, LQR, or cascaded rate/attitude,
pick one at runtime) acts on it, and actuator allocation turns that into
individual reaction-wheel commands through the wheel configuration's
pseudo-inverse. All of that lives in the example, not the engine, so I can
swap controllers without ever touching physics code.

## Challenges

The bug that taught me the most here wasn't actually new, it was a latent
issue the constraint refactor happened to expose. A welded rocket nose cone
stopped rigidly tracking the rocket body under thrust and started visibly
spinning away from it over a few seconds. My first guess was Baumgarte
overcorrection, so I clamped the correction term. Didn't change a thing,
bit-for-bit identical across a 5-second reproduction.

That killed my first theory right away, which is exactly why I'd built a
headless reproduction in the first place: a small standalone program with
the real rocket and nose-cone masses, no GUI, just printing orientation
state every physics step. Running it with `beta = 0` (no position correction
at all) gave the exact same divergence, so the Baumgarte term was never the
problem. Once I instrumented the solver directly, the real cause showed up:
a Cramer's-rule linear solve using an absolute numerical singularity
threshold (`|determinant| < 1e-10`). A 549-tonne rocket's inverse inertia is
naturally tiny in SI units, so the rotational constraint's determinant fell
under that threshold even though the matrix was perfectly well-conditioned.
The rotational correction was quietly returning zero every step at that mass
scale, while the translational half kept working fine and kept feeding a
little unopposed angular velocity into the cone every frame. No crash, no
error, it just silently did nothing, and only at that one mass scale.
