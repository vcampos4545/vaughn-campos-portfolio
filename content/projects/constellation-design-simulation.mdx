## Overview

A tool for exploring satellite constellation tradeoffs: altitude, number of
orbital planes, satellites per plane, coverage, sunlight exposure, and orbital
constraints. Instead of hand-deriving coverage geometry for every candidate
design, the simulator sweeps a parameter space and reports the tradeoffs
directly.

## Problem

Constellation design has a lot of moving parts. Altitude affects coverage
footprint, revisit time, radiation exposure, and launch cost. Plane count and
satellites per plane affect coverage uniformity and cost. Doing this by hand
in a spreadsheet makes it easy to miss interactions between parameters, like
how a small change in inclination can disproportionately hurt coverage at
high latitudes.

The framework needed to:

- Sweep constellation parameters (altitude, inclination, planes, sats per
  plane) quickly
- Compute ground coverage and revisit statistics over a simulated window
- Account for eclipse and sunlight exposure per satellite
- Present results so tradeoffs are legible, not just numerically correct

## Technical Architecture

The simulator has three layers:

- **Orbit propagation core (C++).** Two-body and J2-perturbed propagation for
  each satellite, using Walker-pattern generation to derive orbital elements
  from high-level constellation parameters.
- **Analysis layer (Python).** Ground-track and coverage computation,
  sunlight/eclipse determination, and revisit-time statistics, built on the
  ephemeris exported from the C++ core.
- **Optimization driver.** Sweeps the design space against a coverage/cost
  objective and surfaces Pareto-efficient designs rather than a single best
  answer.

Propagation is the performance-critical inner loop, so it stays in C++.
Analysis and visualization live in Python, where the plotting and numerical
tooling is better.

## Implementation Details

Orbital elements come from Walker constellation notation (`i:T/P/F`), then get
propagated with a J2-perturbed model to keep secular drift (nodal regression,
apsidal rotation) consistent over the simulation window. Ground coverage is
computed by discretizing the Earth's surface into a grid and, at each
timestep, checking satellite-to-grid-point visibility against a minimum
elevation angle.

A cylindrical shadow model flags eclipse periods per satellite, which feeds
power-system sizing discussions even though power modeling itself was out of
scope here.

## Challenges

Performance was the main issue. Naive nested loops over satellites, time
steps, and ground points scale poorly. Vectorizing the coverage computation
and keeping propagation in C++ instead of Python made full parameter sweeps
interactive rather than an overnight batch job.

Presentation was the second challenge. Raw coverage numbers don't communicate
tradeoffs well on their own. Comparative plots (coverage vs. altitude,
coverage vs. satellite count) made the tradeoffs legible to technical and
non-technical reviewers alike.

## Results

The framework reproduced expected coverage trends (diminishing returns per
added satellite at fixed altitude) and made it possible to compare candidate
constellations side by side in minutes instead of days of manual analysis.

## Lessons Learned

Keeping performance-critical propagation code separate from analysis and
visualization code paid off. Each layer got to use the right tool for the job.
It was also a good reminder that simulation work is as much about designing
legible outputs as it is about correct physics.

## Future Work

- Add J4 and drag perturbation terms for longer-duration simulations
- Extend the optimizer to consider ground-station downlink windows
- Add inter-satellite link feasibility analysis for mesh-networked constellations
